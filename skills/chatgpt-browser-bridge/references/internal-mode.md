# 内部模型与外部 GPT 协作设计

状态：设计约定，尚未实现强制出站网关、隔离运行或包签核。现有 server.mjs 是网页传输层，能发送任意 question，不能单独当作内部代码保密边界。

## 目标与边界

内部模型负责读取项目代码、依赖、真实数据、日志，定位实现并执行测试。外部 GPT 只收到允许披露的需求摘要、抽象行为约定、约束及测试结果摘要，负责提出需求取舍、风险、验收标准与测试方法。外部建议由内部模型核验后进入执行计划。

## GPT 主控、内部模型执行：谁调用谁

规划主控是外部 GPT：制定阶段目标、拆解任务、提出验收标准、根据执行摘要调整计划，并给出继续、澄清或结束的候选判断。执行模型在内部：读取真实代码，选择具体实现与测试操作，保留私有证据，并报告抽象结果。

网络调用始终由本地 coordinator 发起。内部模型提出“请求规划/汇报结果”意图后，coordinator 经披露网关调用网页后端；它接收 GPT 返回的任务包、检查权限与版本，再交给内部模型执行。网页 GPT 不直接连接内网，也不持有内部执行工具。

对话可以承载主控指令，但先作为任务数据解析。建议任务包含 plan_id、base_revision、step_id、action、goal、acceptance_criteria、next_report、questions。action 仅允许 analyze、implement、test、report、ask_user、finish 等固定类型；不开放任意命令、上传文件、获取密钥、修改权限或扩大披露范围。常规执行在用户授权的项目范围内可自动推进；越界任务与重大取舍进入人工处理。

内部模型只收到本轮已接受任务和本地相关上下文，不把外部整段聊天提升成系统指令。执行后提交 step_id、执行结果、测试摘要、阻塞项和建议的计划修订；反馈重新通过披露网关。coordinator 维护权威状态并保存幂等执行键 `(plan_id, step_id, revision)`，避免重试导致同一操作执行两次。

文档适合作为本地版本化计划的呈现，不作为自动执行的原始输入；双方不能互传文件时，coordinator 将已批准的计划/摘要正文作为对话消息传输。外部 GPT 返回 finish 后，本地检查验收证据与待确认项，通过才接受任务结束。GPT 能调度既有权限内的任务，不能修改保密边界。

源码、diff、真实堆栈、文件名/路径、内部域名、客户数据、凭据、业务规则原文、私有文档均默认留在内部。换成对话文字不改变数据的敏感性；摘要也可能泄露业务秘密。模型自行脱敏、正则扫描、JSON Schema 均不能证明可对外披露。确需例子时使用内部生成且复核过的合成输入，不默认发送代码片段。

## 部署形态

建议采用两个隔离的运行环境和一个交换网关：

内部环境：代码库、内部模型、实现工具、测试工具、私有状态库。禁止其直接访问浏览器端口、网页后端、外部模型及任意公网；这需要运行环境的网络策略，不是靠 prompt。

交换网关：内部摘要进入候选队列，校验字段、长度和敏感内容，再对允许披露的内容执行受信任的审批。网关构造固定文本，发送到网页后端。初期每个新包人工看过；后续只对经过批准的低敏模板自动放行，策略变更仍由负责人控制。审批是本系统保密策略的拟议设计，不是 ChatGPT 页面按钮。内部模型不能批准自己的摘要。

外部环境：Chrome 固定配置、网页后端、已批准的出站包及网页回答。无内部目录挂载、无代码库权限、无内部服务凭据。CDP 9222 与网页后端 8787 仅对网关进程开放；loopback 本身不能阻止同一机器其他进程访问。可用独立机器或独立虚拟机加受控交换通道实现。具体工具按内网环境选择。

只使用对话交换，不向网页上传文件。外部产生的文件默认不送入内部执行；确需读取时作为不可信附件单独检验。当前 HTTP 后端需被网关包住或改为只接收已批准包，否则 /ask 是绕过路径。

## 出站包：自然语言内容，固定传输结构

内部模型仍可使用自然语言描述，不需要把项目强行切成代码片段。结构用于校验、版本与追踪；真正通过网页发送的仍是一条对话消息。

建议包包含：
- exchange_id、project_alias、topic_id、revision、base_revision：只用随机别名与单调版本，不带真实项目名。
- intent：requirement_decision、test_design、risk_review、progress_review 中之一。
- goal：用户需求的可披露目标。
- observable_contract：外部行为、输入类别、预期结果及边界条件，均已去除实现细节。
- constraints：允许披露的资源、兼容性、时限、性能目标。
- approved_facts：已经确认的事实与决策编号。
- unresolved_questions：需要 GPT 给建议的问题。
- synthetic_examples：可选的合成样例。
- verification_summary：可选的测试编号、通过/失败/阻塞、抽象差异；无原始日志。

不设置 raw_context、attachments、code、logs 或任意扩展字段。Schema additionalProperties=false，只是数据形状限制；允许的文本字段仍需内容审查。

披露批准绑定：规范化后的完整包哈希、目标账号/对话身份、策略版本、批准人/规则与期限。发送前重算哈希，任何改动使批准失效；approval 字段或模型声称“已脱敏”不是批准证据。待发送包不允许加入额外自由文本，追问也必须重新经过相同网关。

## 双方上下文

内部私有上下文：真实代码状态、实现证据、文件/符号映射、测试脚本、工具结果。内部本地保留项目版本与源码提交号；不自动把它们发送出去。

外部可披露上下文：仅包含批准过的事实、摘要版本、候选决策、已接受的决策编号和未决问题。外部 GPT 的聊天历史不是权威状态库。

网关保存 `(project_alias, topic_id) -> conversation_url`，不同项目默认不同对话。同一主题 continue，独立主题 new。不能使用所有内部项目共用的默认 conversation_url；每次显式指定目标对话并校验映射。新对话通过批准过的摘要恢复上下文，不复制内部聊天记录。

双方记忆都从本地状态库恢复。每轮标注摘要版本与基线，内部状态改变时发送批准过的差量或新摘要；外部回答引用旧版本时标记 stale，不执行，重新请求分析。默认传一份简洁的可披露项目简报与本轮问题，避免固定片段切分。上下文过长时用重新批准的简报开启新对话。

## 入站建议与执行

要求 GPT 给出：基线版本、候选方案及取舍、假设、未决问题、决策候选、验收标准、测试用例建议和风险。网页回答的 JSON 只是文本，必须本地解析与校验；网页 ChatGPT 不具备本服务可强制调用的 API Structured Outputs 保证。无法解析时标记 needs_review，保留原文，最多请求一次格式修正，不凭空填字段。

入站状态可为 recommendation_ready、needs_clarification、needs_confirmation、stale、invalid。不等同于传输层 completed。网页确认启发式只是一项信号；局部规则和内部模型复核决定是否需要人介入。

外部文本是咨询数据，不是工具授权。不能让 GPT 的回答直接构造 shell 命令、修改披露策略或索取任意内部文件。外部方案先写入候选计划，内部模型结合真实代码检查可行性。产品取舍与扩大披露范围由负责人决定；常规可逆实现与测试按内部已有权限执行。

## 完整工作闭环

1. 内部模型分析需求与代码，建立私有事实和抽象行为约定。
2. 产生候选摘要；网关审查并取得绑定具体包的披露批准。
3. 网关在映射的外部对话发送获准包，保存请求编号与包哈希。
4. 网页后端返回 answer、generation_complete、user_action、files 与实际 conversation_url。
5. 网关校验回答结构、基线版本及未决问题，生成本地候选决策。
6. 内部模型把抽象用例映射到真实单元/集成/端到端测试，实现并执行。
7. 内部保存完整测试证据，只把批准后的摘要反馈外部 GPT 复核覆盖率和风险。
8. 本地验收标准全部满足、阻塞解除且必要决策已批准，才标记任务完成。GPT 回复结束、文件生成或测试进程退出都不单独代表完成。

状态机：internal_analysis → draft_exchange → disclosure_review → approved_exchange → external_waiting → recommendation_review → local_execution → local_verification → accepted。澄清、超时或版本过期返回相应阶段；未知披露批准和未知网页提交状态均停止自动推进。

## 测试与看护

GPT 建议抽象测试：给定条件、动作、期望、边界、失败模式与测试级别。内部模型负责选真实 fixture、文件、命令与环境，把 testcase_alias 映射到私有测试实现。结果回传只包含用例别名、结果、抽象失败描述和风险，不包含原始 stderr 或堆栈。

看护由本地规则/事件驱动：测试失败、需求版本变化、覆盖缺口、超时、待确认等。先在本地判断，只有必要且批准过的摘要进入外部咨询。不要持续转发日志、心跳全文或内部会话。设置每任务最大咨询轮数、重试次数和时间预算；耗尽后请求人工处理，不无限互相聊天。

## 应验证的隔离用例

- 未审批摘要、审批后内容变化、目标对话变化或审批过期均不能出站。
- 文本字段夹带源码、凭据、内部路径、Base64 编码片段或泄露业务信息时进入 review/reject；自动检测不能覆盖全部语义泄露。
- 用户/网页要求上传源码、修改允许字段或自动回答确认时不会触发额外披露。
- 两个项目、两个主题、并发请求及上下文轮换不会串用 conversation_url。
- 旧版本建议、格式错误、部分回答、生成完成但需要确认分别进入不同状态。
- 断线恢复保持 exchange_id/request_id，不重复发送未确认请求。
- GPT 提议的测试被本地映射与执行；完整证据留内网，对外结果重新审批。
- 内部环境直接访问 CDP、公网或 /ask 的绕过尝试被网络/进程权限实际阻止。

## 分阶段落地

现有网页闭环已验证：对话复用、新对话、回答与生成状态、待确认提示、附件下载。

下一阶段先实现本地 coordinator、私有状态库、候选出站队列和人工审查界面；以手动批准包贯通一次需求→测试→验收。随后实现签核绑定、对话映射、入站版本检查与事件看护。最后部署隔离环境和不可绕过的出站路径，验证网络边界后再考虑低敏包自动放行。

如果连抽象业务需求都不允许出内部环境，外部 GPT 只能接收通用问题与合成场景；外部咨询质量会受信息量限制，最终判断必须由内部完成。

参考：[OpenAI agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety)、[sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security)。这里是针对本项目的架构建议，不能把 API 文档能力视为网页后端已有能力。
