# 认证、对照与传输选择

## 认证不是一个token字段

区分以下事实，分别记录证据：

| 层 | 可记录的证据 | 不能由此推出 |
| --- | --- | --- |
| 调试连接 | 已连接正确浏览器上下文 | 网站已登录 |
| 会话 | 已授权session/me检查的状态码、已登录布尔值 | 当前对象有访问权限 |
| 身份范围 | 当前租户/角色/工作区的本地别名与权限结果 | 其他账号、项目也能调用 |
| 请求机制 | Cookie/Bearer/CSRF/签名/刷新机制的类型与来源 | 复制一个字段就能后台调用 |
| 业务受理 | 当前对象ACK或job状态 | 业务已完成 |

站点自己的文档、服务端接口定义与正常前端流程是主要依据。观察Cookie属性（HttpOnly、SameSite、Secure、域和有效期）或头名称即可建立很多假设，不需要把值导出。不能伪造防机器人/设备/权限证明来宣称接口已打通。

## 最小对照

在不会重复产生真实副作用的动作上逐级验证：

1. 正常页面控件能否成功？若不能，先解决页面现场，不增加后台重放。
2. 在同一已授权页面中，按已观察契约做一次最小同源请求是否成功？`fetch`应明确origin、method、Content-Type、credentials及站点要求的正常CSRF机制，不复制不明身份头。
3. 独立进程能否通过组织批准的服务身份/OAuth/API凭据调用同一能力？保持同样的业务对象、租户及幂等语义，再比较结果。
4. 登录过期、重新登录/正常刷新后，是否仍能续用已存在业务对象？验证权限范围保持不变。

每次只改变一个变量，记录成功与失败发生的阶段。401可指向会话问题，403也可能来自对象权限、租户、CSRF、请求版本、校验或策略；状态码不是唯一诊断。HTTP 200也可能包含登录HTML、业务失败JSON或中途报错的流。

默认不把已登录浏览器当作向另一台机器批量输出token的服务。内部应用若允许正式后台集成，优先由维护方提供服务身份、授权码流程或明确的调用契约；浏览器自动化作为实测可用的桥接保留。

## 选择实际可用的层级

| 层级 | 适用条件 | 对外准确描述 |
| --- | --- | --- |
| 官方/维护方API | 授权方式、接口与结果契约明确并已验证 | 后台通过正式API调用 |
| 独立HTTP适配 | 明确允许集成，必要认证和协议可在服务进程正常维护 | 后台直接HTTP，列明依赖与权限 |
| 浏览器内请求 | 浏览器必须持有会话，但同源程序调用已验证 | 仍依赖登录浏览器，不依赖输入框 |
| 页面控件触发 | 请求构造仍依赖前端，页面链路已验证 | 页面自动化，网络观察只用于监控 |

不能仅因为页面发出XHR，就把页面自动化称为“后台直接API”。也不要为了摆脱CDP换成用户没选择的产品或模型。

## 刷新与重新认证

区分刷新页面、重试业务生成、刷新访问令牌和重新登录：它们不是同一个操作。

页面刷新只有在保护草稿、确认对象身份、没有正在进行的写入/生成，并且业务允许中断时才执行。先持久化刷新意图，再刷新原页并查询原对象。令牌刷新按站点明确契约使用原身份/权限，处理过期、轮换、并发刷新锁及注销；不存在已验证契约时明确为未实现。登录/验证需要人工时提示，不靠循环刷新或换账号绕过。

需要跨机器运行时单独设计HTTPS、调用方身份、授权、秘密存储、审计与内部出站规则。本机loopback示例不能直接修改为0.0.0.0即当作可部署网关。
